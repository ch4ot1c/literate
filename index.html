    Chapter 1: The Core Loop

    In high-performance systems, we must avoid "dynamic allocation" — the act of creating or resizing data while our main loop is running. Doing so forces the system to trigger "garbage collection," a background cleanup that hunts for unused data, causing your application to stutter.

    This code is an excellent example for real-time systems. In modern managed languages, your code does not own memory; the environment does. If you create new objects inside a high-speed loop, you rapidly exhaust available memory, forcing the system to pause your code to "take out the trash."

    While this rarely crashes simple apps, it is the primary reason for "janky" or stuttering performance in games and real-time tools. By pre-allocating, you guarantee your code runs at a constant, smooth speed, regardless of how long the application stays open.

    However, this approach is bad for general-purpose application development. It is verbose, less flexible, and forces you to decide on "maximums" (like maxEntities = 10000) before the app even runs. For most web forms or standard business logic, you should prioritize developer speed and code readability over this level of manual memory control. Use this pattern only when you are building systems that demand high-frame-rate consistency or processing millions of data points per second.
